# Memintelli-Flash v2.2：Mode0/Mode1统一S1/S2执行设计

## 1. 目标

以当前包含S1和S2的DAC研究版本为代码基线，保留已经验证的mode0实现，并把mode1差分对仿真纳入同一套状态预算和紧凑GPU执行体系。最终发布GitHub `v2.2`分支和`v2.2.0` tag，发布包同时支持优化后的mode0与mode1。

主性能验收点为Qwen9B、mode1、read variation=0.05、batch=1、seq=128、warmup=1、repeat=10、full Linear replacement including lm_head。v2.2 mode1必须相对本地v2.1同口径端到端延迟至少降低20%，并快于同机同口径的当前v3 mode0。Qwen4B作为第二验收点。

## 2. 语义边界

Mode1保持以下仿真流程：

1. signed activation经过有限精度DAC量化；
2. 每个weight映射为独立的`G+`和`G-`差分电导分支；
3. read variation=0.05时，两个分支分别生成独立的电导噪声；
4. 差分电流在ADC前形成；
5. 每个input tile独立执行ADC；
6. ADC结果乘tile-local weight scale并以FP32累加到Linear输出。

优化可以改变状态的存放位置、生命周期、GPU任务划分和等价计算顺序，但不能删除双分支噪声、per-input-tile ADC或tile-local scale。

正确性策略：

- read variation=0.0：与同版本mode1 BF16 reference路径比较，要求有限输出、cosine similarity大于0.999，并通过预先固定的allclose阈值。FP32诊断路径额外报告严格误差。
- read variation=0.05：不要求不同随机运行逐元素一致。比较输出分布、logit统计、top-1 agreement和任务指标，并确认`G+`/`G-`使用独立噪声。
- ADC、scale和最终输出累加保持FP32；VMM、电压和恢复后的电导默认BF16。

## 3. S1：Mode-Aware Budgeted State Execution

### 3.1 Mode1状态模型

当前planner只使用mode0的slice状态公式。v2.2新增mode-aware估算接口，并为mode1显式计算：

- 原始或量化weight；
- 两个compact conductance index分支；
- tile-local weight scale；
- 当前output block的noisy differential conductance工作集；
- 预计算signed DAC电压；
- FP32 direct-final输出；
- prefetch窗口与resident state。

planner不能把mode1按mode0的input/weight slice数量估算，也不能把双分支索引错误计成单分支。

### 3.2 输出分块与驻留预算

沿用S1统一接口：

- unlimited budget：完整compact state驻留GPU，作为speed端；
- finite budget：planner选择output block宽度和跨层resident state；
- zero resident budget：只保留当前working block，作为最低显存端。

output block适用于所有宽Linear，不把lm_head shard数量作为公开算法参数。手工block宽度只用于debug和planner敏感性验证。

### 3.3 S1验收

- unlimited mode1相对无S1的额外端到端延迟不超过5%；
- planner预测的CUDA peak误差目标小于10%；
- Qwen9B mode1可在24GB约束下完成full-model forward；
- 预算变化只改变状态策略，不隐式改变S2 kernel或数值路径。

## 4. S2：Mode1 Compact Differential Execution

### 4.1 Signed DAC复用

将signed DAC量化从mode1 VMM kernel的每个output tile循环中提出。每个Linear输入只计算一次`Vin`，随后由所有output chunks复用。

Q/K/V或gate/up共享同一activation时，inter-Linear coalescing进一步共享`x_max`和`Vin`。该共享不合并weight mapping、read noise或ADC状态。

### 4.2 Budget-Selected Noisy Differential Restore

read variation=0.05时，对S1选择的当前execution window执行：

```text
compact G+ index + independent noise -> noisy G+
compact G- index + independent noise -> noisy G-
noisy G+ - noisy G- -> BF16 noisy Gdiff working block
```

只生成一个`Gdiff`工作集，不创建成对的全层浮点`G+`和`G-`。工作集宽度由S1预算决定：

- speed端：显存充足时，execution window覆盖整个Linear输出，生成完整layer-local noisy `Gdiff`，以较大的VMM任务和更少的restore/launch换取速度；
- budgeted端：显存受限时，将相同计算按output chunk执行，并与下一chunk restore重叠；
- minimum-memory端：只保留能够完成一个array-aligned output block的最小`Gdiff`工作集。

完整`Gdiff`只在当前forward的当前层内有效。read variation开启时不能跨forward复用同一noisy `Gdiff`，避免把动态read noise错误变成固定weight noise。实现可以复用预分配workspace，但每次forward必须重新生成噪声状态。

这一步复用mode0已经验证的compact-index restore、runtime noise addressing、execution-window planning和prefetch机制，但使用mode1独立双分支噪声地址空间。

### 4.3 单VMM Direct-Final

新的mode1 direct-final kernel消费预计算`Vin`和chunk-local `Gdiff`：

```text
for each input tile:
    BF16 VMM(Vin_tile, noisy_Gdiff_tile)
    FP32 per-tile ADC
    FP32 tile scale
    accumulate to final Linear output
```

相对现有mode1 pair-index kernel，它消除重复DAC量化、kernel内双分支噪声生成和两次branch VMM，同时保留双分支噪声和ADC边界。

### 4.4 Reduction与shape dispatch

提供两种内部调度，但不作为两种用户模式：

- owner-compute：一个program拥有一个output tile并遍历其input tiles，直接store最终结果，不使用atomic；
- grouped-atomic：当input tile数量过多导致owner-compute寄存器或occupancy退化时，多个group并行并进行FP32 atomic accumulation。

dispatcher根据tokens、input tiles、output tiles、chunk宽度和GPU架构选择。选择规则由离线microbenchmark固化，不在运行时执行sweep。

### 4.5 零variation路径

read variation=0.0继续保留现有pair-order BF16 reference用于正确性。可增加compact signed-difference index作为可选优化，但只有在端到端收益明确且满足正确性门槛时才进入默认路径。v2.2的主要性能收益必须在read variation=0.05成立，不能依赖零噪声特化完成验收。

## 5. S1与S2的组合

S1决定一次允许多少mode1状态驻留GPU，以及output block和noisy `Gdiff` execution window的范围；S2决定每个window内部如何完成DAC、双分支噪声、差分VMM、ADC和finalize。

两者必须正交：

- 相同S2语义和kernel family可在unlimited、24GB和最低resident预算下运行；
- 改变S1预算不能切换到较慢或不同语义的mode1 backend；
- S2 restore工作块大小从S1计划读取：unlimited允许full-layer `Gdiff`，有限预算自动选择chunk，但不修改resident policy或ADC语义。

## 6. 实现边界

主要修改：

- `memintelli/NN_layers/state_planner.py`：增加mode-aware workspace估算；
- `memintelli/NN_layers/linear.py`与`output_blocking.py`：mode1 block/resident/prefetch集成；
- `memintelli/pimpy/data_formats_multimode.py`：mode1 compact state和可复用DAC状态；
- `memintelli/pimpy/memmat_tensor_multimode.py`：mode1 restore/direct-final dispatch和计数器；
- `memintelli/pimpy/triton_fast_accumulate.py`：双分支noisy-Gdiff restore、precomputed-V direct-final和两种reduction schedule；
- `examples/20_real_llm_prefill_benchmark.py`：统一mode0/mode1 S1/S2接口、benchmark manifest和fallback验收；
- focused tests：planner、noise independence、single-Linear correctness、full-model fast-path contract。

不做与该目标无关的模型结构重构，不发布论文数据、Nsight文件、服务器脚本和临时结果。

## 7. 性能诊断与选择规则

先冻结三条同版本路径：

- v2.1 local：当前pair-index mode1 direct-final；
- v2.2 pair-direct：只加入统一S1接口和DAC复用；
- v2.2 chunk-gdiff-direct：加入chunk-bounded noisy-Gdiff restore和单VMM direct-final；
- v2.2 full-gdiff-direct：使用完整layer-local noisy-Gdiff workspace，作为speed端。

对QKV、gate/up、down和lm_head分别记录：

- layer latency；
- restore、VMM/ADC/finalize时间；
- kernel count和median kernel duration；
- CUDA peak；
- fast-path success/fallback计数。

只有满足以下条件的机制进入默认发布路径：

- Qwen9B read_var=0.05端到端至少比v2.1快20%；
- 同口径快于当前v3 mode0；
- Qwen4B不发生明显回退；
- speed端允许显著增加CUDA peak，但必须报告相对v2.1的额外显存，并保持在Pro6000可运行范围内；
- 24GB预算点可运行；
- 无静默fallback。
